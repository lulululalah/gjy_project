## 0. 总体架构（两层解耦）

设计文档第 2 节的「离线合成+训练 / 在线推理+去除」两段式流程，落地为**两层**，
中间用 `schema.FaceGraph` 这个数据契约解耦：

```
brep_defeature/                     说明                                   依赖
├── schema.py        ★契约：FaceGraph + 三层标签 + 归一化 + 类别枚举        numpy
│
├─ ML 管线（纯 torch，跨平台，已测）───────────────────────────────────────
│  ├── synth/graph_synth.py   OCC-free 合成面图生成器（开发/测试替身）       numpy
│  ├── graph/build.py         FaceGraph -> PyG Data                          torch, pyg
│  ├── graph/window.py        k-hop 局部窗口采样                              torch, pyg
│  ├── models/gnn.py          多任务 GNN（语义/实例边界/操作）               torch, pyg
│  ├── instancing.py          逐边亲和度 -> 连通分量 -> 实例                  numpy
│  ├── metrics.py             mIoU / 实例检测 F1 / 操作准确率                 numpy
│  ├── train.py               多任务训练 + 类别权重 + 窗口                    torch, pyg
│  └── infer.py               推理 -> 逐面语义/实例/操作                      torch, pyg
│
└─ OCC 几何后端（pythonocc-core，需 conda 环境）──────────────────────────
   ├── occ/extract.py    STEP/Shape -> FaceGraph（与 synth 同契约）
   ├── occ/inject.py     程序化注入铆钉/孔 + BOP 历史「注入即真值」
   ├── occ/features.py   三类凸起几何：钉子 / 半球 / 梯台
   ├── occ/defeature.py  BRepAlgoAPI_Defeaturing 删除补平 + 校验 + 恢复误差
   └── occ/anchors.py    锚点 STP 读写 + 投影求法向

scripts/                  面向真实模型的工作流脚本（命令行）
tests/                    pytest（ML 11 项 + OCC 7 项）
```

**关键解耦点**：无论 `FaceGraph` 来自 `synth`（无需 OCC）还是 `occ.extract`（真实
STEP），下游训练/推理/评估代码完全一致。因此 **ML 管线可在没有 OpenCASCADE 的机器
上独立开发/测试**，几何后端在 Windows/conda 环境接入。这正是设计文档「让 GNN 直接
在面图上学习」的工程化前提。

## 2. 逐文件说明（代码 → 设计意图）

### 2.1 契约层
- **`schema.py`**（设计 §3.4 / §4.1 / §4.2）
  `FaceGraph / FaceNode / EdgeRecord`；枚举 `Semantic`（背景/铆钉/孔/窗口/贴花/倒角）、
  `Operation`（保留/删凸起/填孔/合贴花/删倒角）；节点 16 连续特征 + `surface_type`
  one-hot；边 5 连续特征 + `curve_type` one-hot；`NormStats` 归一化；JSON 读写。
  **这是「真实数据与合成数据共用同一管线」的关键。**

### 2.2 ML 管线（跨平台，`tests/test_pipeline.py` 覆盖）
- **`synth/graph_synth.py`**（设计 §3 的「OCC-free 开发替身」）
  程序化造「背景面网格 + 植入铆钉/孔子图」并直接给三层真值。
  设计要点：单面阈值不可分，必须靠边的拓扑上下文 → 真正考验图/窗口。
- **`graph/build.py`**（设计 §4）：`FaceGraph → PyG Data`，无向边展开为双向，
  连续块归一化 + 类别 one-hot；携带 `y_sem / y_op / edge_y(same_instance)`。
- **`graph/window.py`**（设计 §4.3）：以面为种子取 k-hop 子图，背景下采样。
- **`models/gnn.py`**（设计 §5）：共享 NNConv 编码器 + 语义头/操作头/边亲和度头。
- **`instancing.py`**（设计 §5.1）：并查集对「预测同实例的特征面边」做连通分量。
- **`metrics.py`**（设计 §7.2）：语义 mIoU/PRF、操作准确率、实例检测 F1（IoU 匹配）。
- **`train.py` / `infer.py`**（设计 §5）：多任务加权损失、窗口训练、整图评估、推理输出。

### 2.3 OCC 几何后端（`tests/test_occ.py` 覆盖，需 conda）
- **`occ/extract.py`**（设计 §4）：STEP/Shape → `FaceGraph`；`face_id` 用确定性
  `TopTools_IndexedMapOfShape` 下标（呼应设计 §9 的「面标识稳定性 T1」）。
- **`occ/inject.py`**（设计 §3）：在干净 shape 上 Fuse/Cut 注入铆钉/孔，用 BOP
  历史（Modified/Generated）把工具面映射到结果面 → 注入即真值，无需 STEP 往返。
- **`occ/features.py`**（设计 §3.2/3.3）：三类凸起 `make_nail / make_hemisphere /
  make_frustum`，底部沉入表面以保证布尔压印。
- **`occ/defeature.py`**（设计 §6）：`BRepAlgoAPI_Defeaturing` 逐实例删面补平，
  `BRepCheck` + 体积变化阈值，失败回滚；`recovery_error` 做注入逆操作自验证。
- **`occ/anchors.py`**：锚点 STP 读写 + 投影到最近面求法向（供脚本使用）。

### 2.4 真实模型工作流脚本（`scripts/`，本阶段新增，**超出原设计文档**）
原设计文档假设「程序化合成数据」。本阶段为了在**真实飞机模型**上交互式造数据，
新增了一条「Rhino 交互选位 → 记录 → OCC 加工/打标」的链路：

| 脚本 | 作用 | 运行环境 |
|---|---|---|
| `rhino_place_rivets.py` | Rhino 内：沿选中边放半球铆钉；**默认只放置+记录 JSON，不改原模型** | Rhino 8 |
| `rhino_imprint_rivets.py` | Rhino 内：把贴合到面上的压印圆作为曲线记录（安全，不改 brep） | Rhino 8 |
| `make_features.py` | OCC：在面板后缘程序化批量放半球（启发式占位，待 DL 替换） | conda OCC |
| `inject_features_view.py` | OCC：把铆钉 STP 逐 solid 融入 + Polyscope 截图 | conda OCC |
| `fuse_from_records.py` | OCC：据 Rhino 记录 JSON 稳健融合（默认安全叠加，保全所有部件） | conda OCC |
| `imprint_from_records.py` | OCC：据记录在**参数域**造圆 + `BRepFeat_SplitShape` 压印子面（无布尔） | conda OCC |
| `label_rivets.py` | OCC：把放好钉的 STP 打成**面级真值**（`--centers` 用记录 JSON，最稳） | conda OCC |

> 这条 Rhino 链路对应设计 §3「数据合成」的一个**人工交互变体**：把「程序化随机注入」
> 换成「人选位置」，但「注入即真值」的思想不变——位置记录进 JSON，标签由
> `label_rivets.py` 据记录可靠产出。

## 6. 已知限制 / 本阶段如实结论（重要）

设计文档 §9 把「OCC 几何修补对样条面的效果」列为待验证项。本阶段实测结论：

- **简单/规则实体**（立方体、Y-20 多为分离 solid）：布尔注入、删除补平、参数域压印
  **均可靠**（OCC 测试通过；Y-20 融合 33→33 solid 有效）。
- **真实复杂模型（如 747sp）**：主蒙皮是**曲面 NURBS + 裁剪域 + 开壳 + 多部件**，
  在其上稳健做几何编辑很难：
  - 整体布尔会**丢件 / 塌成碎块**；
  - 参数域压印（`BRepFeat_SplitShape`）在**平面面可靠（box 6→9）**，但在**曲面裁剪域
    常切不出（747 8052→8052 未增面）**。
- 因此目前 `fuse_from_records.py` **默认走「安全叠加」**：整机原样保留 + 铆钉作为
  独立实体并入同一 compound（**绝不丢件**，面数只增不减），但铆钉未与蒙皮拓扑焊接。

**结论**：监督信号链路（记录位置 → 据记录打面级标签）一直稳健，**不依赖**几何是否
完美焊接。真实复杂模型上的「真正拓扑融合/压印」仍是开放问题，是后续重点。

## 7. 建议的下一步（供讨论）

1. **优先**：用「几何编辑可靠」的模型（如 Y-20）`occ/inject.py` 批量生成**带真值**
   的训练集 → 在真实数据上端到端训练 GNN（补上 M2/M4 的真实数据验证）。
2. 真实复杂模型的拓扑融合/压印作为**独立攻坚**：标定凸凹符号、容差、UV→世界尺度，
   或改用更稳的局部重建策略。
3. 推进 M6（窗口/贴花/倒角）、M7（网格/仿真加速比业务验证）。
